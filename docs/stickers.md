# 表情包补充

文字和表情独立发送。主 Planner 决定是否说话，Replyer 正常生成文字；文字取得成功回执后，再启动独立的表情 sub-planner，决定是否补一张图。表情只补充情绪和语气，不改正文，也不让正文等待选图。本版不做纯图替代文字、定时检查或无人发言时主动开场。

## 配置与素材

要求 `reply.mode = "planner"`、`tools.enabled = true`，使用当前规划模型：

```toml
[stickers]
enabled = true
catalog = "data/sticker_review/catalog.json"
search_limit = 6
target_turns_min = 3
target_turns_max = 5
recent_window = 20
max_image_bytes = 8388608
max_age_seconds = 20
```

`catalog` 相对于配置文件目录，图片路径相对于 `catalog.json`。本地配置已开启；仓库和容器模板默认关闭，因为发行镜像不包含个人挑选的图片。当前素材库共 170 张，D001、A037、A041 尚待复核，因此 167 张可用。描述的生成方法见 [表情包预处理](sticker-preprocessing.md)。

```sh
uv run atri check
uv run atri serve
```

`check` 加载目录并显示可用数量，不调用模型或发送 QQ 消息。文件存在性、哈希及解码在实际发送前校验。更新配置、描述或图片后重启 ATRI。

## 一轮回应的流程

1. 主 Planner 和 Replyer 复用原有消息合批、固定快照、工具查询和过期检查。主 Planner 只提供 `reply`、`wait`、`observe` 及普通查询工具，不再提供 `prepare_reply`、`send_sticker` 或 `search_stickers`；正文不会接到选图或配图指令。
2. 文字独立提交 OneBot。只有确认 `sent` 且有消息 ID 时，才启动本群的一次后台补图任务。主批次立即结束，不等补图；旁听、等待、文字失败或未知、`/health` 和自动复读都不触发补图。
3. 补图复用这轮冻结快照、实际发送的文字（包含输出标点替换）、人设及本群最新频率统计。程序用当前目标消息、已发正文和主规划的交流理解在本地检索默认六个候选，不额外调用模型总结上下文。近期图片降低排序优先级，无候选直接结束。
4. 独立规划器通常调用一次模型，通过原生行动 `supplement_sticker` 返回 `sticker_id` 与简短 `reason`。编号只能取自本次候选，`null` 表示不发；不能传入文件路径、URL、群号或额外正文。格式或模型失败最多重试两次，仍受总时限约束。
5. 选图后校验并准备图片，单独提交一条只包含图片段的 OneBot 消息。它有独立的消息 ID 和发送回执；不再生成搭配文字，不会拼进前一条消息。

表情规划强调：图片可以只补充情绪，不必增加新信息，不能因为文字已完整就一律拒绝图片；同时尊重上下文中的“不要图片”“只要文字”等要求，候选不贴切时不发。

## 时效与并发

每群最多有一个未完成的补图任务，没有待补图队列，也不跨轮次积压。不同群隔离，模型请求共用现有全局并发上限。

`max_age_seconds` 默认 20 秒，从文字确认后启动任务算起，到图片提交前为止；等待模型槽位、规划重试和图片准备都计入。过期就丢弃，文字结果保持成功。它不是轮询周期或人为发送延迟。

同群出现任何新的普通消息时，保守地取消尚未提交的补图，避免沿用旧语境；即使新消息在文字等待回执时到来，这轮也不启动补图。消息去重、其他群的消息和 `/health` 不打断本群补图。睡眠、更新的自身回复、关闭服务也会使未提交任务失效。

已经提交的图片无法撤回其网络投递：后续新消息不会取消对其回执的等待，仍按原发送超时处理。此时不再排入新的补图任务。关闭服务时会取消等待，未确认的发送保持 `unknown`，不自动补发。

## 频率、回执与历史

每个群按已确认成功的自然文字回应统计轮次。默认平均每 3～5 轮补一张，是独立规划器的软目标；当前这轮文字也计入间隔。达到下限后优先考虑贴切图片，未达到时也允许特别合适的补充。没有随机抽签、硬性配额或“欠图补发”。实际频率仍需观察群聊效果。

文字与补图使用同一个 `turn_id`，图片记录额外携带 `parent_message_id`，但两次发送使用不同审计 key，互不覆盖回执。补图成功时只给原文字轮次标记已用表情，不增加第二轮、不再次累计发言活动、不延长普通回复冷却。延迟的图片回执也会归属原轮次，重启后从日志恢复同样的统计；旧版图文合并记录仍能读取。

两条消息分别在确认成功后进入历史。图片使用 `[表情 M001：……]` 一类可见画面标记，方便理解群友后续反应；规划理由、用途、Base64 和本地路径不会冒充已发送的聊天。图片准备失败、发送失败或未知时，已成功文字仍留在历史，图片不进入成功历史，也不推进表情频率。

## 动图与部署

应用以图片内容交给 NapCat，两个容器无需共享素材路径。动画 WebP 转为多帧 GIF，静态 WebP 转为 PNG，原始文件保持不变；转换结果使用有上限的内存缓存。

迁移时把整个 `data/sticker_review/` 放进 Compose 挂载的 `data/`，保留描述和图片的相对路径。需要包含本次代码的应用版本，旧 `v0.1.0` 镜像不会自动获得功能。

## 试聊与日志

先进行几轮普通聊天，观察文字是否先发、图片是否出现在独立消息里；再试“只用文字”“不要图片”“不用回复”。文字确认后马上追加新消息，可验证旧补图会被取消。

`stickers` 日志记录 `[启动补图]`、`[补图候选]`、`[补图决定]`、`[取消补图]`、`[丢弃补图]` 和 `[补图失败]`；模型日志中的用途为 `sticker`。审计的 `sticker_plan` 记录与两次 `delivery` 通过父消息关联，`search_event_logs` 可查询。自动测试和模型模拟不连接 QQ，客户端实际显示仍需试聊确认。
