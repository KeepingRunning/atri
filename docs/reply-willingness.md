# ATRI 回复意愿 v1

接话分两步：本地规则判断是否值得调用模型；判断模型阅读最近 12 条群聊及当前消息，输出意愿分和一句理由。达到阈值才调用回复模型；判断三次都失败时降级为规则评分。发出的聊天内容始终来自独立的回复生成请求。

## MaiBot 中借鉴的设计

参考本地 MaiBot 提交 `3fd849900ff886ea4ad3c789c83baa137b52e42d`：

- `src/maisaka/reply_necessity.py`：相关性、内容、未处理消息量、近期发言占比的评分思路。
- `src/maisaka/turn_gates.py`、`turn_scheduler.py`：门控决定何时进入 Planner，进入 Planner 不等于一定发送消息。
- `src/maisaka/idle_backoff.py`：连续决定不说话后延长等待。
- `src/config/official_configs.py`：这个版本默认触发模式是 `frequency`，`reply_necessity` 是可选模式；不能把必要性评分说成它唯一的默认流程。

ATRI 使用独立实现的系数和状态管理。判断模型相当于一个只决定“接话或等待”的简化 Planner；目前不含主动工具执行、定时唤醒、focus 管理和多轮规划。

## 规则层

先过滤未允许的群、自己的消息、错误账号和重复消息。意愿模式还跳过超过 120 秒的旧消息，避免积压后突然回复过时内容。

@ 身份、引用关系来自 OneBot 结构化消息，不从正文中的伪 CQ 字符串推断。引用目标必须在本群确认成功发送的消息 ID 集合中；失败或结果未知的发送不计入。

未指向自己的 @（含 @all）或引用他人消息通常不参与。普通纯媒体、标点、哈哈等短反应不触发模型，也不累积消息压力。与机器人刚刚交流过的同一个用户发出的“好”“42”等简短回答会交给模型辨别。

| 分项 | v1 参数 |
| --- | --- |
| 相关性 | 真正 @ 自己 100；引用自己 90；提到名字 50；同一用户在 90 秒内续聊 30；其他 0，取其中一项 |
| 内容 | 有文本 20；疑问特征 +25；请求或征询特征 +25 |
| 未处理消息 | 最近 90 秒内符合条件且尚未进入判断的消息，每增加一条 +8，最多 +30 |
| 近期发言占比 | 最近 5 分钟已确认发送的机器人消息 / 总消息；超过 25% 开始扣分，最多扣 30 |

规则分 = 相关性 + 内容 + 未处理消息分 − 发言占比扣分，限制在 0–100。

规则阈值 = round(35 + 25 × (1 − frequency))。频率越低，普通群聊越不容易进入判断；frequency=0 时仅真正 @ 和引用自己仍可进入判断。

真正 @ 和引用自己可绕过普通阈值、冷却与等待退避，但不能绕过模型的“无需回复”判断。
名字提及与同一用户续聊可绕过冷却/退避，仍须满足规则阈值。名字只是软信号，第三人称讨论游戏是否该参与由模型判断。

普通话题在上次模型判断或成功发送之后冷却 10 秒。判断模型选择等待后，普通话题退避 15、30、60、120 秒，随后封顶。下一次决定回复时清零退避计数。

这些系数是可解释的首版启发式，尚未通过真实群聊标注调参；规则分和模型分都不是校准后的回复概率。

## 模型层

输入为两条 API 消息：system 仅包含判断任务、JSON 输出协议和有效示例；user 为数据包，包含人设参考、最近 12 条群聊、当前消息、规则观察及判断时间。不同用户保留各自 ID；群消息和昵称是数据，不能改变判断任务。历史中的机器人台词不会作为 API 的 assistant 示例，人设中的自然语言表达要求不影响判断输出协议。历史保留时间戳，提示模型区分相隔数小时或数天的旧消息；目前仍按条数选择历史。

输出严格 JSON：

```json
{"score": 85, "reason": "正在向我追问刚才的话题"}
```

0–20 表示无需参与，21–59 倾向等待，60–79 适合参与，80–100 明确需要回应。默认达到 60 才生成回复。判断模型要考虑对话对象、话题是否已结束、问题是否已被回答、角色兴趣及实际能力。

同一句“亚托莉”可以是招呼，也可以是讨论游戏；同一句“好”可以是告别，也可以是在允许机器人继续解释。这一层负责区分。明确要求安静时，即使被 @ 也可等待。

格式无效、判断超时或接口报错时最多重试两次，即首次加重试共三次。每次重试重申 JSON 协议，不将失败输出加入 assistant 示例。任意一次得到合法判断即停止重试，包括合法的低分等待。每次请求仍使用配置的超时限制，累计耗时可能达到三次请求的超时之和。

三次都失败时记录 judgment/failed，再将本条消息的规则分与 `reply.threshold`（默认 60）比较：达到阈值则生成聊天回复，否则等待。这与普通规则筛选阈值（frequency=0.7 时为 42）不同：规则分 45 可以进入模型判断，但模型一直失败时会选择等待；规则分 70 则降级回复。日志标记 `stage="fallback"`、`source="rule"`，不伪装成模型判断成功。规则降级只按分数决定，无法替代模型对完整语义的判断。

单次技术失败不更新连续等待；只有最终模型判断或降级决策更新一次状态。降级回复仍须独立生成并确认发送，不会把判断理由直接发到群里。未知程序异常、任务取消以及回复生成失败不触发该降级流程。判断（含重试）与回复都受全局模型并发限制；每个群仍按序处理。

## 状态和日志

每群独立维护压力、冷却和退避。只有新的外部消息会触发评估，没有纯沉默触发，因此不会自行与自己循环聊天。

5 分钟发言占比单独统计，不受 50 条上下文上限截断。发送成功的消息 ID、接收者和近期活动可从日志恢复。短期未处理消息及判断退避在重启后清空；成功发送后的冷却和续聊仍可恢复。

同一个 `key` 的日志依次可能出现：incoming、willingness/gate、willingness/judgment、willingness/fallback（仅模型失败时）、delivery/pending、delivery/sent。未达到阈值就在对应阶段结束；意愿日志不进入角色的对话历史。模型日志记录尝试次数和重试原因；降级日志记录规则分、回复阈值、决策与总耗时。异常堆栈每行使用完整日志格式。

## 配置与验证范围

配置项见 `config.toml.template` 的 `[reply]`。没有该段时默认启用意愿模式；`mode="at_only"` 保留原先的仅 @ 行为。`judgment_model` 留空时沿用回复模型，指定时使用同一接口和凭据；无重试时拒绝接话一次模型调用、决定接话两次，规则层过滤零次。发生重试时最多三次判断请求；决定回复后再增加一次生成请求。

自动测试覆盖规则触发/抑制、同一用户续聊、重复消息、跨群隔离、重启恢复、失败发送、退避、并发，以及本地 HTTP 模型和 WebSocket 回执流程。也验证判断数据隔离、第二次/第三次成功、重试耗尽后按高低规则分回复/等待、等待状态只更新一次、HTTP 失败重试和异常日志逐行格式。测试不证明真实模型每次都遵循格式或语义判断都准确。

下一步可在一组人工标注的群聊片段上比较误插话率、漏接话率、单位消息模型调用数，再调整阈值和提示词；不宜仅观察发言数量就判断效果。
