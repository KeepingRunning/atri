# Planner 与 Replyer

新流程使用 `reply.mode = "planner"`。这是一版可以试聊的实现，效果仍需人工判断；保留 `willingness` 和 `at_only` 便于对比。没有 `[reply]` 的旧配置继续使用 willingness。

实际群聊的问题、证据和后续验证要点见 [2026-09-14 群聊日志复盘](chat-review-2026-09-14.md)。冷却内直接忽略的行为已决定保留；2026-09-15 已调整回应目的与重复内容的提示词，其余改进方向仍待讨论。本文描述当前代码行为，修改提示词后需重启服务生效。

## 一批消息如何处理

1. OneBot 校验群、账号和消息去重后立即存盘；夜间消息结束处理。
2. 同群只有一个 worker。连续消息安静两秒后合批，持续收集最多八秒、最多三十二条。不同群共用模型并发上限。
3. 检查过期、主动频率和普通发言冷却。普通文本、反应或图片不再经过话题关键词评分，由模型结合聊天理解。频率为零时仍只考虑真正 @ 或引用已发送回复。
4. 在取得模型槽位后建立快照，再运行 Planner。快照包含本批消息、近一小时历史、实际构造时间和当前日程。新消息继续记录，但不能修改已交给模型的快照。
5. Planner 选择查询、回复、等待或旁听；只有 reply 才进入 Replyer。Replyer 读取同一份原始快照、规划交接及实际工具结果，输出纯聊天正文。
6. 发送前检查睡眠和是否有相关补充。统一通过 Bot 发送，拿到确认回执才写入自己的发言历史。每批最多发送一条。

普通聊天在冷却内到达时会结束本批，不调用模型；消息仍保留在近期历史中供后续批次阅读。没有定时主动发言，也不为沉默群持续请求模型。

## 行动协议

使用 Chat Completions 原生 `tools` / `tool_calls`，工具描述和 JSON Schema 随请求提交。提示词解释行动规则；程序仅根据校验通过的调用执行，不解析正文里的“应该回复”。规划器每步只能调用一个动作或一个查询工具，禁止混合发送多个最终动作。

目标消息和可引用来源同时写进当轮 schema 的 `enum`；校验失败会返回具体错误类别供重试纠正。规划使用独立 `temperature = 0.2`，正文的生成参数保持原配置。`llm.thinking = "disabled"` 时使用 `tool_choice="required"` 强制产生工具调用，其他情况下用 `auto` 并在程序侧校验；DeepSeek 的思考模式不支持 `required`，依据 [官方 API 说明](https://api-docs.deepseek.com/api/create-chat-completion/)。

| 行动 | 作用 |
| --- | --- |
| `reply` | 指定本批目标消息，交给 Replyer 写回复；此工具本身不发送 |
| `wait` | 等待补充，有新消息提前唤醒；到期也只重新判断一次 |
| `observe` | 结束本批并旁听，等待下一批新消息 |
| 历史查询 / `inspect_image` | 执行现有工具，把真实结果交还 Planner 决定下一步 |

最终动作都带简短的 `understanding`（自由概括话题、互动关系、参与价值）及 `reason`，用于调试。记录的是判断结论，不要求模型输出长篇思维过程。

reply 还需提供：

- `target_message_ids`：只能引用当前快照 pending 里的消息。
- `purpose`：本轮准备接什么话、表达什么反应，与 `interaction` 的判断一致，不写成品台词。覆盖选定对话中仍相关的未答问题和本批多条消息。
- `reference_facts`：有助于本轮理解和准确表达的事实及其来源，消息用 `msg:<消息号>`，当前日程用 `routine:current`，成功工具结果用 `tool:<调用号>`。可以为空，也可以只作背景，不要求正文逐项复述。
- `interpretation`：不确定的解读，与事实分开。
- `style_hint`：可选的自由口吻与表达方式建议（不需要时为空字符串），没有预设的主题或风格枚举。重申承诺、提醒或建议等内容安排归 `purpose`，不夹带在风格提示中。

情绪反应、表达态度和自然接话本身可以完成一次互动，无须每次附加建议或帮助。再次确认、提醒或安排旧事项，应有当前选定消息或相关未答问题中的具体需要，例如追问、重述请求、纠正或条件变化。不能仅为保持约定有效、显得热心，或凭没有当前依据的隐藏意图猜测追加旧任务；也不能只看最后一句像收尾，就遗漏当前需要回答的问题。没有新的相关需要时，换说法、时间或方式再次提供同一帮助，也算重复安排；回应完当前互动即可结束，不自动追加帮助邀约或行动催促。

Replyer 结合近期已确认发送的内容，省去交接中对当前互动没有作用的重复确认和补充，保留追问、重述请求与必要澄清。上述三个字段的职责也写入原生工具 schema 的 `description`，只增加模型可读说明，字段及校验约束保持不变。这些是通用提示词约束，不增加主题模板、程序关键词过滤或模型调用阶段；仍需通过实际对话检验效果。

程序能检查来源是否存在，无法保证模型对来源的转述完全正确；Replyer 也会看到原始证据并被要求核对。规划内容不作为已发生事实加入下一轮聊天。

## 日程和睡眠

以下睡眠规则默认启用。临时夜间试聊可设置 `schedule.sleep_enabled = false` 后重启，所有睡眠检查随之关闭，凌晨使用夜晚日程；恢复时设回 `true`。普通回复意愿、冷却与消息过期判断仍按原配置执行。

仍从本地日常库每两个小时按时段随机选取，两小时大日程和当前十分钟小格进入同一快照。Planner 把它作为兴趣与状态的弱背景，Replyer 作为当前虚构生活背景；普通话题不必硬提日程，过时自述不能推翻当前背景。

00:00–08:00 强制禁止回复，夜间接收的消息不排入回复队列，也不会在早晨自动补进 Planner 的近期聊天快照。每次模型请求、工具执行、后续请求和实际发送都检查睡眠。跨午夜后不重试、不补发；明确查询历史仍使用存盘档案。午夜前已经提交给 OneBot 的消息无法撤回其网络投递。

## 等待与草稿作废

默认每批最多主动等待一次、最多八秒；有新消息会提前唤醒，再短暂合并拆句。等待不占模型并发槽位。

如果目标发言人继续说话、有人引用目标消息、直接呼叫或提到 ATRI，程序保守地认为可能有补充。规划/生成期间出现这类新输入会丢弃草稿，最多合入新消息重建一次快照。再次失效或本批已满则结束旧批，留给后面的排队消息触发新判断；不会把旧草稿发出。

这只是关联检查，不是语义话题识别：同一个人突然换话题也可能触发重建，另一人不带引用的纠正可能漏判。新群聊消息本身不会无限延长正在处理的快照。

## 配置与预算

`[planner]` 的完整参数及注释见 [配置模板](../config.toml.template)。普通路径通常调用一次 Planner、一次 Replyer。每批最多两轮只读查询，且受 tools.max_calls 限制；这版每步只查一个工具，因此默认最多执行两次。工具预算与缓存在等待、重规划期间保持，不重新发放。

单次规划调用失败或行动不合法，首次加两次重试；失败输出不进入后续提示词。三次都失败时本批记录 failed，不套用旧版分数做降级。Replyer 失败也不发送部分正文。旧 willingness 模式仍保留原有评分降级。

快照默认最多 32000 字符，首先移除较旧历史，单条正文最多 2000 字符；本批过长会进一步裁剪并标注。连元数据也装不下时明确失败，不截断成坏 JSON。该预算不等于整个请求的 token 上限：还要加人设、行动 schema、交接和工具结果，工具结果由 `tools.max_result_chars` 与调用数限制。超大人设或小窗口模型仍需要调低预算。

## 日志和试用

控制台可搜索 `[收集消息批次]`、`[聊天快照]`、`[行动决定]`、`[等待补充]`、`[生成正文]`、`[快照已过时]`、`[本批结束]`。Planner 为粉紫色，Replyer 为浅绿色；保留现有工具、日程及模型颜色。快照 ID 把一次规划和正文生成联系起来。

同群 JSONL 增加 `snapshot`、`planner`、`batch` 记录，与 `incoming`、`delivery` 共存，但不进入对话历史。快照记录保存 ID、消息 ID、历史数量、裁剪数，完整快照只留内存；planner 记录最终行动参数和判断结论，不保存服务商私有 reasoning。历史日志查询仅返回诊断字段，不把规划交接当成群友事实。

```sh
uv run atri check
uv run python -m unittest discover -s tests -v
uv run atri --log-level INFO test-planner
uv run atri serve
```

`test-planner` 使用当前模型和人设，跑拆句合并、要求安静、无 @ 分享和历史查询四组模拟群聊。临时数据不会写进真实群，发送器只收集结果，不连接 QQ。它使用当天 14:35 的虚构日程背景，关闭主动等待及看图；通常约 7–10 次真实模型请求，失败会按正式协议重试。

无 @ 分享只展示模型选择，不把“必须插话”作为正确答案。四项通过表示这组样本的流程可运行，不能证明回复自然。等待、中途补充、群隔离、睡眠和看图等边界由离线测试覆盖，后续仍需试聊观察。
